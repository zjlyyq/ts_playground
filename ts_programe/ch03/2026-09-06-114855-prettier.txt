⏺ 在 ESLint 的输出中，可以通过以下方式判断：

  1. 运行时加 --fix-dry-run

  npx eslint . --fix-dry-run

  这个命令会模拟修复，显示哪些文件会被修改，但不实际写入。

  2. 看输出中的提示

  运行 eslint . --fix 后，如果有可修复的问题，会看到类似：

  ✖ 26 problems (4 errors, 22 warnings)
    3 errors and 2 warnings potentially fixable with the `--fix` option.

  最后一行的 X problems potentially fixable with the --fix option
  就告诉你有多少个可以自动修复。

  3. 查看规则文档

  每条 ESLint 规则的文档页会标注 🔧 Fixable：

  # 查看某条规则的详情
  npx eslint --print-config file.ts | grep "规则名"

  或者访问 eslint.org/rules，规则名旁边有🔧图标的就是可修复的。

  4. 你这次运行的情况

  上一轮 47 个问题，修复后剩 26 个，说明 21 个被自动修复了（主要是 Prettier
  格式问题和 prefer-const）。剩余的 4 个 error 和 22 个 warning
  都不可自动修复，需要手动改代码。

⏺ 以下是 4 个 error 的逐一分析：

  ---

  1. types.ts:4 — no-useless-assignment

  let c = a + b;  // ← 第一次赋值
  // ...
  c = add(1, 4);  // ← 第二次赋值，覆盖了上面的值
  console.log(c);

  原因：c 的初始值 a + b 在被读取之前就被第 12
  行重新赋值了，第一次赋值是无用的。

  是否修复：✅
  建议修复。这是真实的问题，虽然不影响运行结果，但会造成误解。可以改为：

  let c: number;  // 先声明
  c = add(1, 4);

  ---

  2. types.ts:18 — prefer-as-const

  const b3: false = false;

  原因：ESLint 认为写 const b3 = false as const 或直接 const b3 = false
  更好，因为 const 声明 + 字面量值已经自动推导为字面量类型，不需要手动标注 : 
  false。

  是否修复：❌
  可以不修。这是教学代码，故意展示"如何手动指定字面量类型"，保留标注反而更清晰。

  ---

  3. types.ts:24 — prefer-as-const

  const n4: 3 = 3;

  原因：同上，const n4 = 3 已经自动推导为类型 3，手动标注 : 3 是多余的。

  是否修复：❌
  可以不修。同样是教学代码，目的是演示字面量类型的写法，保留更好理解。

  ---

  4. types.ts:56 — prefer-const

  let o2: { b: number; c?: string; [key: number]: boolean };
  o2 = { b: 100, c: 'hello', 100: true, 200: false };

  原因：o2 声明为 let，但之后没有再被重新赋值，ESLint 认为应该用 const。

  是否修复：⚠️ 看情况。如果后面还需要重新赋值给 o2，保留
  let；如果确定不会改，改成 const 更安全。教学场景中保留 let 也无妨。
