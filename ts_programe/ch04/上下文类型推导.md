**上下文类型推导（Contextual Typing）**，通俗来说就是：**TypeScript 根据“你把这个值用在哪里”（即上下文环境），反过来倒推“这个值应该是什么类型”。**

它是“类型推导”的一种“反向”模式。我们平时最熟悉的类型推导是**“正向推导”**：看初始值来猜类型（比如 `let x = 1` 推导为 `number`）。而上下文推导是**“反向推导”**：看目标位置需要什么类型，来决定当前值应该是什么类型。

这种机制最典型的应用场景就是**回调函数**和**事件监听器**。

---

### 🎯 结合你截图中的示例来理解

#### 案例：`times` 函数（上下文推导生效）

```typescript
function times(f: (index: number) => void, n: number) {
    for (let i = 0; i < n; i++) {
        f(i);
    }
}

// ✅ 调用时，行内函数不需要标注类型
times(n => console.log(n), 4);
```

**发生了什么？**
1. TypeScript 看到 `times` 的第一个参数要求类型是 `(index: number) => void`。
2. 你传入了 `n => console.log(n)`。
3. TS 根据“参数位置”的上下文，知道 **这个位置的函数，其参数必须是 `number`**。
4. 于是 TS 自动把 `n` 的类型指定为 `number`。

**这里的 `n` 没有写 `: number`，但 TS 通过“上下文”知道了，这就是“上下文类型推导”。**

---

#### 案例：非行内声明（上下文推导失效）

截图后面提到，如果你这样写：

```typescript
function f(n) { // ❌ 报错：Parameter 'n' implicitly has an 'any' type.
    console.log(n);
}
times(f, 4);
```

**为什么失效了？**
- 当 TS 解析到 `function f(n)` 这行代码时，它是**孤立的**。TS 此时还没有看到下面 `times(f, 4)` 的调用，不知道 `f` 未来会被放进哪个“洞”（上下文）里。
- 因为没有上下文参照物，TS 无法猜到 `n` 的类型，于是根据 `noImplicitAny` 规则，判定 `n` 是隐式的 `any`，直接报错。

> **关键区别**：**“行内声明”（Inline）** 是直接把函数写在调用参数的位置，TS 可以立即看到“这个位置需要什么类型”；**“非行内声明”** 是变量提前定义，TS 在定义那一刻找不到上下文，所以无法推导。

### 🌰 其他生活中的例子（帮助你秒懂）

- **数组的 `map` 方法**：
  ```typescript
  [1, 2, 3].map(item => item * 2); 
  // item 不需要写类型，因为 [1,2,3] 的上下文告诉 TS，item 是 number。
  ```

- **DOM 事件监听**：
  ```typescript
  button.addEventListener('click', event => {
      // event 不需要写类型，上下文告诉 TS，这是 MouseEvent。
  });
  ```

- **React 的 `useState`**（部分上下文场景）：
  虽然 `useState` 主要靠泛型，但在某些复杂回调中，上下文也帮了大忙。

---

### 🧠 总结一句话

**上下文类型推导 = 看“坑位”猜“萝卜”**。TypeScript 不需要你给每个小函数参数写注解，它看你把这个函数塞进了什么类型的“卡槽”里，就能自动帮你把参数类型补上。这极大减少了冗余的类型标注，是 TypeScript 流畅编码体验的重要基石。😊
