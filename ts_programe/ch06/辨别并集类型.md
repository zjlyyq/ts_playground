这个例子恰恰是 TypeScript 官方文档里**用来解释“为什么需要可区分联合（Discriminated Union）”的经典反面教材**。它揭示了一个非常隐蔽的陷阱：**即便你通过类型守卫（Type Guard）缩窄了联合类型的一个属性，TypeScript 也不一定会自动帮你缩窄同一个对象的另一个属性。**

为了帮你彻底看懂，我把这个例子拆解成“逻辑层面”和“TypeScript 类型检查器层面”来对照解释。

---

### 1. 事件类型的定义

首先，你定义了两个事件类型和一个联合类型：

```typescript
// 文本事件：value 是字符串，target 是 HTML 输入框元素
type UserTextEvent = {
  value: string;
  target: HTMLInputElement;
};

// 鼠标事件：value 是坐标数组 [x, y]，target 是普通 HTML 元素
type UserMouseEvent = {
  value: [number, number];
  target: HTMLElement;
};

// 联合类型：事件要么是文本，要么是鼠标
type UserEvent = UserTextEvent | UserMouseEvent;
```

---

### 2. `event.value` 为什么能成功缩窄？

在 `handle` 函数里，你写了：

```typescript
if (typeof event.value === 'string') {
  event.value; // ✅ 这里 TS 知道是 string
  // ...
}
```

- 因为 `UserMouseEvent` 的 `value` 是 `[number, number]`（数组），它的 `typeof` 是 `'object'`，而 `UserTextEvent` 的 `value` 是 `string`。
- TypeScript 通过 `typeof` 检查，**直接把 `UserMouseEvent` 从联合类型中排除了**。
- 因此，在 `if` 代码块内部，`event` 的类型被缩窄为 `UserTextEvent`。
- 所以 `event.value` 理所当然变成了 `string`。这一步是正常的。

---

### 3. `event.target` 为什么没能缩窄？（核心痛点）

根据正常的逻辑，既然 `event` 已经确定是 `UserTextEvent`，那 `event.target` 按理说应该是 `HTMLInputElement`。

**但是，TypeScript 给出的类型却是 `HTMLInputElement | HTMLElement`** —— **它并没有缩窄。**

> 图片里原文解释说：“`handle` 函数的参数是 `UserEvent` 类型，但这并不意味着一定传入 `UserTextEvent` 或 `UserMouseEvent` 类型的值，还有可能传入 `UserMouseEvent | UserTextEvent` 类型的值。”

#### 这句话怎么理解？

我们要分两层看：

1. **逻辑现实（代码运行）**：`typeof event.value === 'string'` 为真，那这段代码运行时，`event` **100% 是** `UserTextEvent`，`event.target` **100% 是** `HTMLInputElement`。
2. **TypeScript 的类型检查思维（静态分析）**：TypeScript 走的是“基于流的类型推导”。它在检查 `if` 分支时，确实知道 `event` 是 `UserTextEvent`。但是，**对于对象的“关联属性”（Correlated Properties），TypeScript 的检查策略非常保守。**

**真正的技术原因是：** `UserTextEvent` 和 `UserMouseEvent` 这两个类型结构**高度重叠**——它们都有 `value` 和 `target`。虽然 `value` 不同，但 `target` 的类型（`HTMLInputElement` 和 `HTMLElement`）存在**继承关系**（`HTMLInputElement` 是 `HTMLElement` 的子类型）。

TypeScript 害怕一种极端情况：**万一传入的值既符合 `UserTextEvent` 的结构，又符合 `UserMouseEvent` 的结构呢？**（虽然这在你定义的精确联合里不太可能，但在 TypeScript 的结构类型系统中，子类型关系会导致“重叠”）。

为了避免在复杂的继承链中出错，TypeScript 的收窄策略在遇到“非字面量类型”的检查（如 `typeof`）时，**不会将缩窄结果传导给另一个同名但类型不同的属性**。它会采取“并集保守策略”：既然 `target` 在两个类型里都有，且类型不完全一致，那就继续保留为并集 `HTMLInputElement | HTMLElement`。

---

### 4. 如何修复？（引出“可区分联合”）

由于 `typeof` 和 `instanceof` 在处理复杂对象时不够“聪明”，TypeScript 社区推荐使用**字面量类型字段（如 `type` 或 `kind`）**作为区分标志，这就是**可区分联合（Discriminated Union）**。

**修改后的安全写法：**

```typescript
type UserTextEvent = {
  type: 'text';      // 👈 固定的字面量，作为“标签”
  value: string;
  target: HTMLInputElement;
};

type UserMouseEvent = {
  type: 'mouse';     // 👈 固定的字面量
  value: [number, number];
  target: HTMLElement;
};

type UserEvent = UserTextEvent | UserMouseEvent;

function handle(event: UserEvent) {
  // 检查固定的 type 字段
  if (event.type === 'text') {
    event.value;   // ✅ string
    event.target;  // ✅ 现在 TS 知道是 HTMLInputElement 了！
  }
}
```

**为什么这样就有效了？**
因为 `type` 字段的值是**字面量字符串 `'text'` 和 `'mouse'`**，它们是互斥且不可被继承的。TypeScript 看到 `event.type === 'text'`，就能 **“一刀切”** 地将整个 `event` 精确锁定为 `UserTextEvent`，并且**连带把 `target` 也精确锁定为 `HTMLInputElement`**。没有任何歧义。

---

### 🎯 总结（一句话记住这个例子）

这个例子告诉你：**别用 `typeof` 去区分结构复杂的对象属性，因为 TS 不一定能把“缩窄结果”传递给你的其他属性。请给每个类型贴上一个独一无二的**字面量标签 **（比如 `type` 或 `kind`），让 TS 能“精准锁定”整个对象。** 😊
